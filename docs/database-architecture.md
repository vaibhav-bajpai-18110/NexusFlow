# NexusFlow - Database Architecture and Design

## 1. Introduction

NexusFlow is a Visual IoT Telemetry and Rule Engine platform.
MongoDB is planned as the primary database for storing user
information, registered IoT devices, and telemetry records.

The database layer is designed to support real-time data
ingestion, monitoring, and future analytics.

## 2. Database Architecture

The proposed database architecture contains three primary
collections:

- users
- devices
- telemetry

The backend will communicate with MongoDB through Mongoose.
Database connection settings will be managed using environment
variables.

## 3. Collection Design

### 3.1 Users Collection

Purpose:
Stores application user information.

Proposed fields:
- _id: Unique MongoDB identifier.
- name: User's display name.
- email: Unique email address.
- passwordHash: Secure password hash.
- role: User permission level.
- createdAt: Account creation timestamp.
- updatedAt: Last update timestamp.

### 3.2 Devices Collection

Purpose:
Stores registered IoT device information.

Proposed fields:
- _id: Unique MongoDB identifier.
- deviceId: Unique device identifier.
- name: Device display name.
- deviceType: Type of IoT device.
- owner: Reference to the user who owns the device.
- status: Current device status.
- location: Device location information.
- createdAt: Registration timestamp.
- updatedAt: Last update timestamp.

### 3.3 Telemetry Collection

Purpose:
Stores sensor readings generated by IoT devices.

Proposed fields:
- _id: Unique MongoDB identifier.
- deviceId: Reference to the associated device.
- timestamp: Time when the reading was recorded.
- metric: Sensor metric name.
- value: Recorded numeric value.
- unit: Measurement unit.
- metadata: Additional sensor information.

## 4. Entity Relationships

The proposed relationships are:

- One User can own multiple Devices.
- One Device can generate multiple Telemetry records.
- Each Telemetry record belongs to one Device.

References will be maintained using MongoDB ObjectIds.

## 5. Data Flow

The planned database data flow is:

1. An IoT device generates sensor readings.
2. The backend receives incoming telemetry.
3. Incoming data is validated.
4. Valid telemetry records are stored in MongoDB.
5. The rule engine processes telemetry events.
6. The dashboard receives relevant updates through
   real-time communication.

## 6. Indexing Strategy

The following indexes are planned:

- Unique index on users.email.
- Unique index on devices.deviceId.
- Index on devices.owner.
- Index on telemetry.deviceId and timestamp.

These indexes are intended to improve lookup performance
and support device-specific telemetry queries.

## 7. Time-Series Storage Strategy

NexusFlow plans to use MongoDB Time-Series Collections
for high-volume telemetry storage.

Proposed configuration:

- Time field: timestamp
- Metadata field: deviceId
- Granularity: seconds

The final configuration and retention policy will be
validated during implementation.

## 8. Data Validation

The database layer will enforce:

- Required user name and email.
- Unique email addresses.
- Required device identifiers.
- Allowed device status values.
- Valid telemetry timestamps.
- Numeric telemetry values.
- Valid references between users, devices, and telemetry.

## 9. Security Considerations

- Passwords must never be stored in plaintext.
- Database credentials must remain in environment variables.
- Sensitive configuration files must not be committed.
- Database access should follow least-privilege principles.
- Incoming data must be validated before storage.

## 10. Implementation Plan

The planned implementation milestones are:

1. Configure MongoDB connection.
2. Implement User, Device, and Telemetry models.
3. Add schema validation and indexes.
4. Configure environment variables.
5. Test database connectivity.
6. Verify model operations.
7. Integrate database operations with backend services.

## 11. Current Status

This document describes the initial database architecture
and design for NexusFlow Day 1.

The actual database connection, model implementation,
and integration testing are pending.
