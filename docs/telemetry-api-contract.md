## 1. Introduction

NexusFlow is a Visual IoT Telemetry and Rule Engine platform designed to collect, process, monitor, and visualize data generated by IoT devices.

This document defines the proposed API contract between the frontend and backend components. It explains how telemetry data will be submitted, how the server will respond, and how different components will communicate with each other.

The purpose is to maintain a consistent data format throughout the application.

## 2. Objective

The main objectives of this API contract are:

- Define a standard telemetry data format.
- Establish communication between frontend and backend.
- Define API request and response structures.
- Maintain consistency in device and sensor identification.
- Support real-time telemetry monitoring.
- Prepare a foundation for future rule-engine integration.

## 3. Telemetry Data Structure

Each telemetry record should contain the following fields:

| Field | Description | Type |
|---|---|---|
| deviceId | Unique device identifier | String |
| sensorId | Unique sensor identifier | String |
| metric | Sensor measurement type | String |
| value | Measured sensor value | Number |
| unit | Measurement unit | String |
| timestamp | Time of data generation | ISO Date String |

### Example Telemetry Payload

```json
{
  "deviceId": "device_001",
  "sensorId": "sensor_temp_01",
  "metric": "temperature",
  "value": 28.5,
  "unit": "Celsius",
  "timestamp": "2026-11-14T10:30:00Z"
}
```

## 4. API Endpoint Design

### 4.1 Submit Telemetry Data

**Method:** POST

**Endpoint:** `/api/telemetry`

Purpose:
Receives telemetry data from IoT devices or simulated data sources.

Request Body:

```json
{
  "deviceId": "device_001",
  "sensorId": "sensor_temp_01",
  "metric": "temperature",
  "value": 28.5,
  "unit": "Celsius",
  "timestamp": "2026-11-14T10:30:00Z"
}
```

Expected Success Response:

```json
{
  "success": true,
  "message": "Telemetry received successfully",
  "data": {
    "deviceId": "device_001",
    "metric": "temperature",
    "value": 28.5
  }
}
```

### 4.2 Retrieve Device Telemetry

**Method:** GET

**Endpoint:** `/api/telemetry/:deviceId`

Purpose:
Retrieves telemetry records associated with a particular device.

Example:

`GET /api/telemetry/device_001`

Expected Response:

```json
{
  "success": true,
  "deviceId": "device_001",
  "records": [
    {
      "sensorId": "sensor_temp_01",
      "metric": "temperature",
      "value": 28.5,
      "unit": "Celsius"
    }
  ]
}
```

## 5. API Response Standards

All API responses should follow a consistent structure.

Success Response:

```json
{
  "success": true,
  "message": "Operation completed successfully",
  "data": {}
}
```

Error Response:

```json
{
  "success": false,
  "message": "Invalid telemetry data",
  "error": "Required fields are missing"
}
```

## 6. HTTP Status Codes

| Status Code | Meaning |
|---|---|
| 200 | Request successful |
| 201 | Resource created |
| 400 | Invalid request data |
| 404 | Resource not found |
| 500 | Internal server error |

## 7. Data Validation Rules

The backend should validate incoming telemetry data before processing it.

- Device ID must not be empty.
- Sensor ID must not be empty.
- Metric must be provided.
- Value must be numeric.
- Unit must be provided.
- Timestamp must follow a valid date-time format.
- Invalid payloads should return an appropriate error response.

## 8. Real-Time Communication

NexusFlow is designed to support real-time monitoring.

The backend may use WebSocket communication through Socket.IO to transmit newly received telemetry updates to connected frontend clients.

Proposed event name:

`telemetry:update`

Example Event Payload:

```json
{
  "deviceId": "device_001",
  "metric": "temperature",
  "value": 28.5,
  "unit": "Celsius"
}
```

This allows the frontend dashboard to display updated sensor values without repeatedly requesting the server.

## 9. Frontend and Backend Responsibilities

**Frontend Responsibilities:**

- Display device and sensor information.
- Send requests using the defined API structure.
- Display telemetry values.
- Handle loading and error states.
- Update dashboard information through real-time events.

**Backend Responsibilities:**

- Receive telemetry requests.
- Validate incoming payloads.
- Process telemetry information.
- Store valid records using the database layer.
- Return standardized API responses.
- Broadcast updates through real-time communication.

## 10. Future Integration with Rule Engine

The telemetry API will provide the foundation for the NexusFlow rule engine.

In future development, telemetry values can be evaluated against user-defined conditions.

For example:

- Temperature greater than 35°C.
- Humidity below 30%.
- Device status changes.

When a configured condition is satisfied, the rule engine can generate an appropriate event or alert.

## 11. Conclusion

This API contract establishes a common communication standard for NexusFlow frontend and backend development.

It provides a structured approach to telemetry submission, data retrieval, validation, and real-time updates.

The specification will help team members develop their respective components independently while maintaining compatibility during integration.
